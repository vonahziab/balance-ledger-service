# ADR-0002: Идемпотентность списания

**Статус:** принято

**Контекст:** клиент может повторить `debit` (таймаут, обрыв соединения).
Повтор не должен списывать деньги второй раз и должен вернуть тот же
ответ, что и исходный запрос.

**Решение:** обязательный заголовок `Idempotency-Key`. Ключ хранится прямо
в `balance_ledger`:

- колонка `idempotency_key varchar(255)` с `unique (user_id, idempotency_key)`
  — пространство ключей своё у каждого пользователя;
- колонка `balance_after` — снэпшот баланса сразу после операции.

Под блокировкой пользователя ([ADR-0003](0003-concurrency.md)) сервис ищет
запись с парой `(user_id, key)`:

- не найдена — обычное списание;
- найдена, `amount` совпадает — возвращается `balance_after` и `id` этой
  записи, без вставки и пересчёта;
- найдена, `amount` другой — `422 IDEMPOTENCY_KEY_REUSED`. Молча вернуть
  старый результат нельзя: клиент решил бы, что списана новая сумма.

Ключ `NULL` допустим только у сидирующей `credit`-записи
(`CHECK (action = 'credit' OR idempotency_key IS NOT NULL)`), поиск по
ключу её не находит.

**Почему `balance_after`, а не текущий баланс:** после исходного запроса
могли пройти другие списания. Повтор вернул бы другой баланс, и клиент не
понял бы, какой результат дала его операция. Колонка заодно позволяет
проверить инвариант по последней записи ([ADR-0004](0004-balance-recalculation-from-ledger.md)).

**Запоминаются только успешные списания.** Отклонённый запрос (нет средств,
`404`) строки в леджере не создаёт, поэтому повтор выполняется заново. Это
безопасно: ошибка не меняла состояние.

**Рассмотренная альтернатива — отдельная таблица `idempotency_keys`** с
хешем тела и сохранённым ответом. Универсальнее (любые эндпоинты,
запоминает и ошибки), но здесь одна операция записи с одним полем в теле —
лишняя таблица не оправдана.
