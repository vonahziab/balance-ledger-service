# ADR-0003: Конкурентный доступ

**Статус:** принято

**Контекст:** при параллельных `debit` одного пользователя без блокировки
оба запроса могут прочитать один и тот же баланс и оба пройти проверку
средств — овердрафт или потерянное обновление.

**Решение:** одна транзакция (`READ COMMITTED`) на операцию, первым шагом —
`SELECT … FROM users WHERE id = :id FOR UPDATE`. Пока блокировка
удерживается, вся последовательность «проверить ключ → проверить средства →
записать → пересчитать» атомарна для этого пользователя.

`FOR UPDATE` сериализует только операции одного пользователя — разные
пользователи друг друга не блокируют. Транзакция берёт ровно одну
строковую блокировку, поэтому дедлоков между `debit` нет.

**Рассмотренные альтернативы:**

- **Атомарный `UPDATE … SET balance = balance - :amount WHERE balance >= :amount`.**
  Одна команда, овердрафт невозможен. Но это инкрементальное изменение, а
  ТЗ требует пересчёта по истории ([ADR-0004](0004-balance-recalculation-from-ledger.md)).
  Кроме того, усложняются ветки ошибок: повтор ключа проявится как
  `unique_violation` (`23505`) на `INSERT` — его нужно ловить и перечитывать
  исходную запись, а при `0 rows` нужен ещё запрос, чтобы отличить `404`
  от нехватки средств. С `FOR UPDATE` все ветки — обычные проверки по
  порядку.
- **Оптимистичная блокировка (`version`).** Требует цикла повторов при
  конфликте; для частых списаний одного пользователя повторы станут нормой.
- **`SERIALIZABLE`.** Корректно без явных блокировок, но так же требует
  повторов при `40001`.
