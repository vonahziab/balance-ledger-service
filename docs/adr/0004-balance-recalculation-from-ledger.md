# ADR-0004: Пересчёт баланса по истории

**Статус:** принято

**Контекст:** ТЗ требует «пересчёт баланса по истории после каждой операции
в поле balance». Источник истины — `balance_ledger`, а `users.balance` —
производное значение, которое удобно читать и кэшировать.

**Решение:** в транзакции `debit`, под блокировкой пользователя
([ADR-0003](0003-concurrency.md)), сразу после `INSERT` в леджер:

```sql
UPDATE users
SET balance = (
  SELECT COALESCE(SUM(CASE WHEN action = 'credit' THEN amount ELSE -amount END), 0)
  FROM balance_ledger
  WHERE user_id = :id
)
WHERE id = :id
RETURNING balance;
```

Проверка средств и `balance_after` считаются до `INSERT` от заблокированного
`users.balance`. Результат `SUM` сверяется с `balance_after`: если они
разошлись, леджер и `users.balance` рассинхронизированы — транзакция
откатывается с `500` и ошибкой в логе, сомнительное значение не пишется.

Инвариант после каждого `COMMIT`:

```
users.balance = SUM(credit) − SUM(debit) = balance_after последней записи
```

**Цена:** `SUM` — O(n) по истории пользователя под блокировкой. Фильтр по
`user_id` использует индекс `(user_id, idempotency_key)`, `action` и
`amount` читаются из таблицы. Для объёмов задачи это пренебрежимо.

**Рассмотренная альтернатива — инкрементальный пересчёт**
(`balance = balance - amount`). O(1) и тот же результат, пока держится
инвариант, но это не пересчёт *по истории*, как в ТЗ, и рассинхронизация
не ловится на каждой операции. Разумная оптимизация для длинной истории —
тогда `SUM` уходит в периодическую сверку.
